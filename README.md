# Пул соединений

## 1. Замок и условия

Один `ReentrantLock` защищает настройки, признак остановки, очереди свободных соединений и ожидающих, набор активных выдач, счётчики `creating` и `closing`, флаг активности каждой выдачи. `stats()` читает все значения под этим замком.

Все условия связаны с тем же замком:

| Условие | Кого и когда будит сигнал |
|---|---|
| `PoolWaiter.ready` | У каждого ожидающего свой `Condition`. `signalNext()` вызывает `signal()` для первого в очереди, только если есть свободное соединение или место. После получения ресурса, таймаута или прерывания поток проверяет, можно ли разбудить следующего. При остановке `shutdown` сигнализирует каждому ожидающему. |
| `maintenance` | `signal()` будит фоновую очистку при возврате или выдаче соединения, изменении размера и остановке. Очистка ждёт ближайшего срока `idleTimeout`, если свободных соединений больше `minIdle`; иначе ждёт изменения состояния без таймера. |
| `drained` | `signalAll()` при возврате соединения или завершении физического закрытия будит `shutdown`. Он перепроверяет число активных выдач и незавершённых закрытий. |

Ожидания находятся в циклах проверки состояния: Java допускает ложные пробуждения. При `fair = true` замок работает в честном режиме, а очередь `PoolWaiter` разрешает получить ресурс только первому ожидающему. Новый вызов встаёт в хвост, даже если ресурс уже доступен. При `fair = false` обгон разрешён.

## 2. Учёт `total` при создании и закрытии

Под замком выполняется равенство:

```text
total = idle.size() + borrowed.size() + creating
```

Перед вызовом фабрики `borrow` проверяет `total < maxSize` и увеличивает `creating`. Затем освобождает замок. Другие потоки уже видят занятое место и не могут зарезервировать его повторно. При успехе под замком `creating` уменьшается и появляется активная выдача: `total` сохраняется. При ошибке резерв освобождается и ожидающий получает сигнал. Если пул остановлен во время создания, результат фабрики закрывается.

Перед физическим закрытием соединение под замком исключается из учёта пула и становится недоступным для выдачи. `closing` учитывает незавершённое закрытие, но не входит в `total`. Затем `RawConnection.close()` вызывается вне замка; его исключение подавляется. `shutdown` ждёт завершения этих закрытий. Поэтому медленные фабрика и закрытие не удерживают замок и не мешают операциям с другими соединениями.

## 3. Почему внутри пула нет взаимоблокировки

У пула один замок, вложенного захвата разных замков нет. Фабрика и физическое закрытие работают вне замка. `Condition.await()` и `awaitNanos()` освобождают замок на время ожидания. `join()` фонового потока вызывается без замка. Поэтому ожидающий поток не удерживает замок, необходимый другому потоку для завершения ожидаемого действия. Цикл зависимостей замков внутри пула не образуется.

Каждый поток ждёт своё условие внутри второго `borrow`. Первое соединение остаётся у него до выхода из `try`. Свободных соединений и мест нет; вернуть первое каждый собирается после второго запроса. Для запросов `P1`, `P2`, `P3`, удерживающих `R1`, `R2`, `R3`, возможен цикл:

```text
P1 ждёт освобождения R2, удерживаемого P2
P2 ждёт освобождения R3, удерживаемого P3
P3 ждёт освобождения R1, удерживаемого P1
```

Каждому подошло бы любое соединение, но ни один владелец не доходит до возврата. Владение соединениями устанавливается кодом теста и статистикой. JVM видит ожидание `Condition`, при котором замок пула освобождён. Она ищет циклы владения мониторами и синхронизаторами с эксклюзивным владением; выданное соединение для неё обычный объект. Поэтому сообщения `Found one Java-level deadlock` нет, а `findDeadlockedThreads()` возвращает `null`. Минутный таймаут ограничивает зависание, но не даёт запросам успешно завершиться. Тест прерывает его через `shutdown(Duration.ZERO)` после проверки состояния.

Для не более `T >= 1` потоков, каждому из которых нужно не более `C >= 1` соединений одновременно:

```text
maxSize_min = T * (C - 1) + 1
```

Предполагается, что потоки последовательно получают соединения, выполняют конечную работу и возвращают их; фабрика успешно завершается, внешних держателей нет, пул не останавливается и не уменьшается.

**Почему меньше недостаточно.** При размере `T * (C - 1)` каждому можно выдать `C - 1` соединений: пул заполнится, все будут ждать последнее. При ещё меньшем размере можно распределить всю ёмкость так, чтобы каждый держатель имел меньше `C` и ждал следующее соединение. При `C = 1` достаточно одного места; нулевая ёмкость запрещена контрактом и не позволяет обслужить запрос.

**Почему этого достаточно.** Если все потоки ещё ждут соединения, каждый удерживает не больше `C - 1`, вместе не больше `T * (C - 1)`. Значит, остаётся свободное соединение или место: общее ожидание без доступного ресурса невозможно. Если один поток уже получил всё необходимое, он завершает работу и возвращает соединения, позволяя продвигаться остальным. Для обслуживания каждого ожидающего используется честный режим; в нечестном режиме формула исключает общее ресурсное зависание, но не гарантирует порядок обслуживания.

Проверка достаточности в тесте использует `T = 5`, `C` из `{1, 2, 3, 4}` и размер по формуле. После получения `C - 1` соединений все потоки одновременно запрашивают последнее и успешно завершаются. Результат формулы должен укладываться в ограничение `maxSize <= 1000`.
